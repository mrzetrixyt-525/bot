## Node system
The local node uses the local LXC CLI. Dynamic nodes use `node-agent.py`.

On a remote node:
```bash
sudo apt update
sudo apt install -y python3
sudo mkdir -p /opt/rgnodes-node-agent
sudo cp node-agent.py /opt/rgnodes-node-agent/node-agent.py
sudo chmod 0755 /opt/rgnodes-node-agent/node-agent.py
```

Run the agent with the API key generated by `-node create`:
```bash
sudo /usr/bin/python3 /opt/rgnodes-node-agent/node-agent.py --api_key='YOUR_GENERATED_KEY' --host=0.0.0.0 --port=18443
```

The compatible endpoints are `/api/ping`, `/api/get_host_stats`, `/api/get_access_info`, `/api/get_container_stats`, and `/api/execute`.
The agent accepts the key by `X-API-Key` or `Authorization: Bearer ...`; query-string API keys are intentionally disabled so credentials do not leak into URLs/logging.
Restrict the agent port with a firewall/private network where possible because the API uses HTTP unless you place it behind TLS. The bot does not use query-string API-key auth.

## Install / repair
Run as root on the LXD host:
```bash
sudo bash setup.sh
```

The installer is non-interactive and repairs missing packages/configuration. It preserves an existing `.env` and `vps.db`. Node.js 20 is not used as the fallback target; the setup prefers Node.js 24.x LTS in 2026.

It checks/installs, as available:
- Python 3, pip, venv/dev tooling
- build-essential, libffi-dev, pkg-config
- OpenSSH server/client
- curl, certificates, git, unzip and common network/process tools
- QEMU/KVM + libvirt packages when repositories expose them
- snapd/LXD when the LXD CLI is unavailable
- Node.js 24.x LTS (or a newer installed major) + PM2 for process supervision
- `davey`, `PyNaCl`, and all dependencies in `requirements.txt`

### LXD storage behavior
If LXD is not initialized and `/dev/loop-control` is unavailable, the setup uses a deterministic LXD preseed with `dir` storage instead of relying on automatic loop-backed storage selection. Existing initialized LXD configuration is preserved.

## 24/7 process model
Only one Discord bot process is allowed.

```text
systemd
  └── pm2-runtime
        └── Python bot.py
```

A process lock inside `bot.py` and the setup lock prevent duplicate bot gateway sessions / concurrent setup runs.

## Security / stability
- SSH configuration uses an `sshd_config.d` drop-in and validates `sshd -t` before reload/restart.
- LXC command execution does not use shell=True on the host.
- VPS names are sanitized before LXC use.
- Persistent port forwards are reconstructed after restart and use host-bound LXD proxy devices.
- DB writes use SQLite WAL, full synchronization and an application lock.
- Deployment/reinstall/clone paths install the guest baseline and anti-mining guard.
- A background repair task rechecks running managed VPS for missing baseline guest commands and restores them when needed.
- Anti-mining protection is best-effort signature/process detection; it is not a guarantee against a custom/renamed miner and should be combined with host/provider network controls for stronger enforcement.

## Configuration
Copy `.env.example` to `.env` and set at least:
```env
DISCORD_TOKEN=YOUR_DISCORD_BOT_TOKEN
YOUR_SERVER_IP=YOUR_REACHABLE_HOST_IP
PINGGY_ENABLED=true
PINGGY_AUTO_START=true
PINGGY_HOST=free.pinggy.io
PINGGY_SSH_PORT=443
```

Do not use a loopback address such as `127.0.0.1` for a public access endpoint. Leave it blank to use the public-IP autodetection, or set a verified public IPv4/IPv6 explicitly.

## Deep repair notes
The current build specifically addresses the failures shown in the supplied logs/screenshots:
- Debian 11 (`images:debian/11`) was removed from the deployment selector because the configured `images:` alias is no longer reliably available; supported Ubuntu 20.04/22.04/24.04 and Debian 12/13 remain selectable.
- SSH now validates the effective `sshd` configuration, unlocks the root account, and refuses to mark a VPS ready when port 22 is not actually listening.
- Host port reconstruction detects stale occupied ports and automatically moves the persistent forward to a free port instead of repeating `address already in use`.
- IPv6 proxy listeners bind to the node's verified global IPv6 address rather than `[::]`, avoiding the IPv4/IPv6 wildcard bind collision seen in the logs. Public IPv6 is shown only when the node really has a globally-routable address.
- Pinggy uses the current SSH endpoint on `free.pinggy.io:443`; the tunnel is automatically started after deployment, and `Reconnect Pinggy` creates a fresh tunnel.
- The `Reconnect SSHX` and standalone `Pinggy` dashboard buttons are removed. `SSHX` can start a new session; Pinggy is automatic/reconnect-only from the VPS dashboard.
- The reinstall confirmation callback now preserves the VPS owner's ID instead of raising `AttributeError: 'ConfirmView' object has no attribute 'owner_id'`.
- `-maintenance on|off` remains admin-only and now changes the bot presence to a maintenance status while user VPS control actions are restricted.

Third-party tunnels (SSHX/Pinggy) remain dependent on those providers being reachable at the time of connection; the bot treats them as secondary access paths and does not fabricate a working endpoint when a provider is unavailable.

## Dual-stack access
The dashboard reads actual guest IPv4 addresses and globally-scoped IPv6 addresses. SSH over IPv4 uses the node's detected/configured public IPv4 plus the VPS SSH forward. SSH over IPv6 is shown only when a globally-routable IPv6 is actually assigned. A private/ULA IPv6 address is never mislabeled as public.

A routable public IPv6 for every VPS still requires an IPv6 prefix/routing from the upstream provider; LXD cannot invent a provider-routed address. The setup enables managed IPv6 networking for guests, but the dashboard distinguishes global IPv6 from local/private addresses.

## Custom animated emojis
Emoji.gg supports custom Discord emojis and animated effects. The bot supports exact Discord custom emoji codes or names with Unicode fallback. Current Emoji.gg examples verified include `online` and `StatusOnline`; additional names in `.env` are local names for the emojis you upload. ## Ultimate deployment contract
Every managed VPS deployment uses `rgnodes-vps-{VMID}` as the LXC name, installs the guest baseline, attempts Docker installation, configures SSH, records the assigned node, and creates persistent SSH port forwarding. Docker readiness is based on a real `docker info` check; a nested guest where Docker cannot start does not invalidate the LXC VPS itself.

## Public IP truth
The bot never fabricates a public address. `PUBLIC_IPV4` and `PUBLIC_IPV6` are preferred when valid global addresses are configured; otherwise the node attempts automatic public-IP discovery. If the node is behind NAT/CGNAT or the provider blocks inbound traffic, the dashboard reports the public endpoint as unavailable rather than showing `127.0.0.1` as a public address.

## Tunnel isolation
Normal SSH, SSHX, and Pinggy are independent access systems. Their PID files, URLs, reconnect actions, and UI actions are separate.

## Runtime version
The setup upgrades an existing Node.js runtime when it is below v20 and installs Node.js 24.21.0 LTS on supported Linux architectures. Node.js currently lists v24 as an LTS release line; v20 is EOL.
